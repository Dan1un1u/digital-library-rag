# 数字图书馆项目总说明书与四人分工

本文供全组成员阅读，说明要做什么、怎样协作、各人交什么，以及怎样判断项目完成。它同时承担需求说明、概要设计、技术规格和协作约定的作用。配套的四份 AI 任务书可以整篇交给 AI Agent，但成员仍负责提供合法馆藏、配置模型、核验事实并掌握课堂展示内容。

版本为 1.0。计划假设四人、四周、普通电脑运行小规模检索，并使用现成 LLM 服务。尚未确认的课程时长、硬件、API 预算和具体馆藏属于计划假设。本次交付是设计文档包，尚未实现应用，也没有实际实验成绩。

## 1 项目目标与题目

英文题目建议为 Digital Library with an LLM Based Evidence Grounded Search and Question Answering System。

中文题目为 基于大语言模型的数字图书馆证据支撑搜索与问答系统。

系统面向不一定掌握专业术语的读者，让他们用自然语言搜索一个专题馆藏，获得基于原文的解释或比较，并从回答直接找到支持文献。项目的核心成果是一条可核验流程：

用户问题 → 理解或澄清 → 检索文献片段 → 组织证据 → 生成回答 → 点击引用核对原文。

推荐馆藏主题为数字图书馆、信息检索和知识组织。先用 10 篇文本型 PDF 验证流程，再扩展到 50–100 篇。资料选取和实际范围由全组确认，不把全互联网当成可回答范围。

## 3 需求说明

四人分工速览如下。具体步骤和完整交付清单见第 5 节；本表用于开工分配和日常检查。

| 组员 | 一句话职责 | 最重要的交付 | 谁直接使用 |
|---|---|---|---|
| A | 把文献变成可追溯的规范文本块 | LibraryStore、馆藏清单、页面与 Chunk、解析测试 | B 建索引，D 打开文件 |
| B | 把文本块变成可保存、可过滤的三种检索 | Retriever、索引清单、模型适配器、检索实验 | C 取证据，D 展示搜索 |
| C | 把问题与证据变成可核对的答案或追问 | QAEngine、提示词、LLM 适配器、引用评估 | D 展示所有问答状态 |
| D | 把三个模块变成一个可运行应用 | API、界面、配置、启动脚本、总体评估 | 全组运行、验收与展示 |

每个人统一交付代码、测试、运行说明、依赖清单、真实验收记录和约 15 道候选题。

### 3.1 参与者与使用场景

读者使用馆藏浏览、搜索、问答和证据查看。小组成员作为本地管理员导入馆藏、查看失败原因、运行实验。第一版在本地可信课堂环境使用，不做公网权限系统或正式生产部署。

典型场景：

| 场景 | 用户表达 | 系统期望 |
|---|---|---|
| 文献发现 | 找一下 semantic search 的论文 | 返回文献和匹配片段 |
| 缺少术语 | 有没有不用准确关键词也能找到资料的方法 | 识别可能在问语义检索，给出相关文献和有证据解释 |
| 多文献比较 | 关键词检索和语义检索有什么区别 | 按比较维度回答，结论附对应来源 |
| 意图不明 | 图书馆那个智能系统有什么问题 | 先追问是问答、推荐还是编目 |
| 超出馆藏 | 这些资料能证明某方法在所有场景都最好吗 | 不做无依据的普遍结论，说明资料不足 |
| 证据核查 | 点击回答中的引用 | 展开原文并打开正确 PDF 页 |

### 3.2 功能需求与验收

| 编号 | 必须实现的行为 | 主要负责人 | 最小验收 |
|---|---|---|---|
| FR01 | 导入 PDF 与人工核验元数据，显示处理状态 | A，D 装配 | 正常文件可入库，坏文件有明确错误 |
| FR02 | 去重、清洗、按页切块并保留定位 | A | 重复导入不重复建块；片段能回到原页 |
| FR03 | 关键词、向量、混合检索 | B | 同一请求可切换三种方式并返回统一格式 |
| FR04 | 年份和主题过滤，文献级聚合 | B，D 聚合 | 不返回不符合条件的文献 |
| FR05 | 理解日常表达，保留原意改写 | C | 可查看系统理解；改写失败有回退 |
| FR06 | 识别需要澄清的意图 | C，D 交互 | 含糊对象得到追问，选择后可重新请求 |
| FR07 | 依据检索证据生成回答 | C | 有效回答的每条事实结论都有可解析引用 |
| FR08 | 引用、原文和 PDF 页跳转 | C，D | 标题、页码来自真实记录，点击可核对 |
| FR09 | 证据不足、模型不可用的状态处理 | C，D | 不伪造答案，界面说明原因 |
| FR10 | 索引保存、重启加载、失败保留旧索引 | B，D | 重启能检索；重建失败不破坏原有服务 |
| FR11 | 测试题、运行日志、对比评估 | 全员，D 汇总 | 有真实记录及可复现命令 |
| FR12 | 启动文档与演示流程 | D，全员复核 | 新环境按 README 能运行或得到准确缺项提示 |

### 3.3 非功能要求

- 可复现：记录模型、依赖、切块、索引版本与实验参数。
- 可组合：模块边界采用同一数据结构，不让模块各自建设独立应用。
- 可核验：模型不能自行编造标题、页码、链接或原文。
- 可维护：每个人的代码和交付目录清晰，接口变更全组同步。
- 可观察：记录检索、生成与总耗时，提供明确失败原因。
- 可区分：真实模型、mock 演示、自动校验和人工评估分别报告。
- 可靠性以行为验收为主。响应时间和准确率在试运行后设目标，不把未测试的数字写成保证。

可选功能是重排序、连续追问和 PDF 内高亮。完整 OCR、表格推理、知识图谱和微调不属于基础验收。

## 4 概要设计与模块关系

离线链路：PDF 与元数据 → A 提取清洗 → A 存储片段 → B 构建关键词和向量索引。

在线链路：D 接收请求 → C 理解或澄清 → B 检索 → C 选择证据并调用 LLM → C 核查结构与引用 → D 展示回答、来源和原文件。

| 模块 | 输入 | 输出 | 不承担的职责 |
|---|---|---|---|
| A 馆藏与内容处理 | PDF、元数据、切块配置 | 文献、页面、Chunk、文件定位 | 不调用 LLM，不实现检索排序 |
| B 索引与检索 | A 的 Chunk、查询、过滤 | IndexManifest、RetrievalHit | 不生成回答，不管理网页 |
| C 查询理解与问答 | AskRequest、B 检索器、LLM 适配器 | AnswerResponse | 不写馆藏数据库，不建设第二套索引 |
| D 界面与集成 | A/B/C 模块、统一配置 | API、界面、启动与评估入口 | 不另写竞争版本的核心算法 |

同步上传及全量重建足以支撑小馆藏。D 负责锁和状态协调，B 负责索引快照保存。正式展示前冻结馆藏和索引，避免标注片段 ID 改动。

## 5 四人分工与明确交付

### 5.1 A 负责馆藏和可追溯内容

A 的任务是把 PDF 变成其他模块能稳定使用的数据。

执行顺序：

1. 与全组确定馆藏范围，整理来源与使用说明。
2. 用 10 篇样本核对文本提取，重点检查双栏、页码和断行。
3. 实现去重、页面清洗、按页切块和 SQLite 存储。
4. 提供共同规格中的 LibraryStore 全部接口。
5. 扩展馆藏，输出解析质量记录和 15 道候选题。

明确交付：

- src/dlrag/ingestion/ 和 tests/ingestion/；
- 可批量导入的 CLI 与元数据模板；
- 文献清单和来源说明，实际 PDF 通过小组约定方式提供；
- LibraryStore、规范页面文本、稳定文本块 ID；
- evaluation/ingestion/ 解析质量记录；
- handoff/A/ 下的运行说明、依赖、验收记录与候选题。

完成标志：B 能直接得到规范 Chunk；D 能凭 doc_id 打开原文件；相同输入重复导入不会新增重复记录。

### 5.2 B 负责索引与检索

B 的任务是让日常表达和准确术语都能找到相关资料。

执行顺序：

1. 使用手工小样例实现 BM25 和过滤。
2. 接入 embedding，完成归一化精确向量搜索。
3. 使用 RRF 融合，去重并统一返回格式。
4. 保存和重载索引快照，支持失败保留旧索引。
5. 运行关键词、向量、混合三组检索实验。

明确交付：

- src/dlrag/retrieval/ 和 tests/retrieval/；
- Retriever 全部接口、真实 embedding 适配器与测试替身；
- 索引构建/查询 CLI、IndexManifest；
- evaluation/retrieval/ 检索结果、耗时和分析；
- handoff/B/ 下的依赖、验收、候选题与联调说明。

完成标志：C 用同一 search 接口即可检索；D 能切换三种模式；相同索引重启后仍可使用。

### 5.3 C 负责查询理解和证据问答

C 的任务是把问题、检索片段和答案连接起来，并处理澄清与证据不足。

执行顺序：

1. 用 fake retriever 与 mock LLM 实现完整返回结构。
2. 完成意图识别、改写回退、澄清状态。
3. 实现证据选择、提示词、结构化生成。
4. 从真实片段构建引用；非法引用最多修复一次。
5. 接真实模型，记录正确性、覆盖和引用支持关系。

明确交付：

- src/dlrag/qa/、提示词模板与 tests/qa/；
- QAEngine、真实 LLM 适配器、mock 适配器；
- 三类业务结果与错误处理；
- evaluation/qa/ 问答与引用评估；
- handoff/C/ 下的配置、验收、候选题与运行说明。

完成标志：D 无需重新理解模型输出即可展示；每条结论的引用都能解析；模型故障和无证据情况不会伪装成成功。

### 5.4 D 负责界面、装配和总体评估

D 的任务是把三个模块装配为一个应用，并让实验和演示可复现。

执行顺序：

1. 第一周建立工程骨架、API 模型和模拟界面。
2. 按固定接口实例化 A、B、C，不等所有模块完成才开始。
3. 完成上传状态、搜索聚合、问答和来源交互。
4. 汇总依赖、配置、测试题、端到端测试和实验命令。
5. 提供 README、展示讲稿和真实演示记录。

明确交付：

- src/dlrag/api/、ui/、shared/、工程配置与 README；
- scripts/seed_demo.py 和 scripts/run_evaluation.py；
- tests/integration/、本地样例和全组评估数据集；
- evaluation/reports/ 汇总报告与失败案例；
- docs/demo.md 和 docs/presentation_outline.md；
- handoff/D/ 下的集成验收、运行状态与交接事项。

完成标志：按照 README 可启动应用；用户可从提问走到原文；真实与 mock 模式标识清楚；全组结果可复现。

### 5.5 工作量平衡与人工责任

每人约 15 道题，由另一人复核。建议 A 与 C 互审，B 与 D 互审。每人负责自己部分的 2–3 页展示内容和至少一个失败案例解释。D 汇总材料，但不代替其他成员做人工事实核查。

题型配额建议：A 为 exact 10 + multi_document 5；B 为 vague 15；C 为 clarify 10 + unanswerable 5；D 为 multi_document 10 + unanswerable 5，合计 60。允许小组调整，但须保持各类题的覆盖。

每个人至少能解释自己的输入、核心处理、输出、一个测试和一个限制。使用 AI 不能免除这一责任。

## 6 协作与合并流程

### 6.1 开工当天

1. 全组读本说明书，确认角色和馆藏主题。
2. D 建立共同仓库、基础目录和配置说明，将五份文件放入 docs/project/。
3. A 提供 10 篇样本文献和初步元数据；缺实际资料时各模块用自建合成样例先运行。
4. 每人将自己的 AI 任务书交给 Agent，并说明当前工作目录。
5. 用共同规格锁定接口，所有更改通过 D 协调。

推荐每人自己的分支或本地副本；若同一工作目录并行，严格遵守编辑归属。文档不授权 Agent 自动提交、推送、删库或公开发布，具体由用户指令决定。

### 6.2 合并顺序

D 先建立共同配置和模拟依赖 → 合入 A → 合入 B → 合入 C → 完成 UI 与端到端验收。

每次合入都执行对应模块测试和最小集成测试。合并冲突优先保留已确认的接口，不自行把字段改成更方便的名字。

### 6.3 模块未完成时如何继续

| 缺少内容 | 继续方式 | 最终替换 |
|---|---|---|
| A 的真实馆藏 | B 用手工 Chunk，C 用 fake 检索结果 | 换为 LibraryStore 输出 |
| B 检索器 | C 使用实现同一 search 方法的替身 | 注入 Retriever |
| C 模型配置 | D 用明确标注的 mock 问答对象 | 注入真实 QAEngine |
| D 工程骨架 | A/B/C 设置 PYTHONPATH=src 并运行自身 CLI | D 合并打包配置 |

交接文件必须列出替身位置、启动方法和替换方法。不得留下在真实模式里静默启用的 mock。

## 8 验收与课堂展示

### 8.1 全组验收清单

- [ ] 能导入、去重、查看失败状态，并定位文献与页面。
- [ ] 关键词、向量、混合检索返回同一结构，过滤一致。
- [ ] 对日常表达给出合理检索，对真实歧义提出澄清。
- [ ] 有效回答的关键结论都能点击引用。
- [ ] 引文来自原始片段，能打开正确 PDF 页。
- [ ] 证据不足、模型超时、无密钥分别得到明确结果。
- [ ] 索引可重载，失败重建不破坏旧索引。
- [ ] 新成员可按 README 运行；mock 不冒充真实实验。
- [ ] 有约 60 道经过复核的题、开发/测试划分和真实评估记录。
- [ ] 每个成员提交自己模块的实现、测试、交接与展示材料。

### 8.2 实验和指标

B 对比 keyword/vector/hybrid，C 对比基础 RAG 与加入改写澄清的版本；条件允许再评估 reranker。比较时固定馆藏、embedding、生成模型和其他参数。D 统一记录环境、配置和索引版本。

检索报告 Hit@5 和基于标注的 Recall@K；标注不完备时必须说明。跨文献题补充证据组覆盖率。回答采用人工要点评分；引用分别评估支持正确率和覆盖率；澄清与无答案题统计期望行为命中率。耗时报告样本数、中位数和 P95。

引用支持正确率：人工判断的有效“结论—引用”支持关系数 / 全部此类关系数。引用覆盖率：获得充分证据的可核验结论数 / 需要证据的结论数。两项不能用“ID 存在率”替代。

### 8.3 演示安排

12–15 分钟可安排 A 介绍问题和馆藏，B 解释索引，C 解释问答与引用，D 现场演示并汇总实验。现场至少演示日常表达、精确查询、意图澄清和证据不足四类问题，完整点击一次答案引用到 PDF 原页。

讲稿和录屏基于真实运行，不把合成样例伪装为论文内容。预录演示用于网络故障备用，并明确标注。

## 9 设计依据与阅读材料

## 共同规格与集成契约

本节在五份文件中保持一致，版本为 **1.0**。它是接口和数据的共同依据。实现时必须遵守，不得在自己的模块中另起字段或接口。需要变更时，先提交具体变更建议，由组员 D 协调更新总说明书和四份任务书，再同步代码。本文是项目规格，不是已经实现的功能声明。

### 项目范围与默认配置

- 项目：基于 LLM 的专题数字图书馆搜索与证据问答系统。
- 默认馆藏：数字图书馆、信息检索、知识组织主题，50–100 篇具有使用权限的文本型 PDF；先以 10 篇试运行。扫描件识别、复杂表格理解、微调、知识图谱暂不纳入必做。
- 第一版：批量导入及元数据、关键词检索、向量检索、混合检索、意图澄清、单轮带引用问答、证据查看、PDF 页跳转、实验评估。
- 约四周开发；Python 3.11；FastAPI 后端；Streamlit 界面；SQLite；模型与依赖版本在首次可运行后固定。这里的版本是建议基线，应先验证开发机兼容性。
- B 负责 embedding，C 负责生成模型。LLM 提供方通过环境配置接入；真实模型不可用时允许明确标识的 mock 模式。mock 只能证明接口运行，不能作为语义效果或真实回答质量的实验结果。
- 不自动购买服务、上传整个馆藏到外部平台或公开部署。API 密钥由使用者配置；调用外部 LLM 时，仅发送该次问题和选定片段，并在运行说明交代这一点。
- 默认参数：每块约 300–500 tokens、长段落拆分重叠约 50 tokens、不跨 PDF 页；每个检索分支取 20 条；RRF 常数 60；证据最多 6 块，总上下文预算可配置。切块 tokenizer 名称、版本和计数口径须记入索引清单。
- 用实际 tokenizer 计数；如使用字符近似，必须明确记录该模式及字符阈值，不能把字符数报告为 token 数。
- 年份与主题过滤在两个检索分支一致生效。年份为空的文献在指定年份范围时排除；主题过滤为与选中主题至少有一个交集。
- 文件路径在服务端解析；API 不接受客户端给出的服务器绝对路径。原始文件、模型缓存和数据库不放进源码提交。

### 配置键与错误约定

上传 metadata_json 对象只接受 title、authors、year、topics、language、source_url、rights_note。数组、年份和语言按 Document 规则；title 缺失时可用文件名并标待核验；rights_note 缺失时写“待人工确认”，不能自动写成已授权。doc_id、文件哈希、状态和路径由服务端生成，客户端不能覆盖。A 的 metadata 参数使用同一组键。

A.ingest_pdf 的 options 使用下列 ChunkingConfig，D 向 A 传入，并把同一值传给 B 记录在 manifest：

~~~json
{
  "count_mode": "token",
  "tokenizer_name": "<实际 tokenizer 标识>",
  "tokenizer_revision": null,
  "max_tokens": 400,
  "overlap_tokens": 50,
  "max_chars": 1200,
  "overlap_chars": 150
}
~~~

token 模式使用 max_tokens/overlap_tokens，character 模式使用 max_chars/overlap_chars；不用的参数仅保留配置，不混用单位。tokenizer 获取失败不能静默降级，应明确选择 character 模式并记录。character 模式 Chunk.token_count 为 null，额外记录 char_count；这不是实际 token 统计。同一个有效索引不混用切块配置；对已经导入的相同 PDF 要改变切块参数时，A 提供明确的离线重建流程，默认重复导入不重切。重建会改变标注位置，应在冻结测试集前完成。

B 的 settings 使用 candidate_k=20、rrf_k=60、normalize_embeddings=true；模型名称/修订由 embedding_backend 的配置提供。C 的 settings 使用 planning_enabled=true、retrieval_mode="hybrid"、retrieval_top_k=20、max_evidence_chunks=6、context_budget_tokens=6000、max_output_tokens=1000、max_answer_repairs=1。预算是起始配置；C 必须按实际服务上下文上限检查，并预留系统提示和输出，不强行发送超限内容。D 的 baseline 评估可以通过 planning_enabled=false 关闭改写与澄清，记录这项差异。

各模块提供名为 ProjectError 的异常，至少有字符串属性 code/message；可各自定义，不要求共享 Python 类的身份相同，D 按属性处理。推荐固定代码：

| 模块 | 错误码 |
|---|---|
| A | INVALID_PDF、NO_EXTRACTABLE_TEXT、FILE_NOT_FOUND、CHUNK_CONFIG_MISMATCH |
| B | INDEX_NOT_READY、EMBEDDING_NOT_CONFIGURED、EMBEDDING_MISMATCH、INDEX_BUILD_FAILED |
| C | MODEL_NOT_CONFIGURED、MODEL_TIMEOUT、MODEL_UNAVAILABLE、OUTPUT_VALIDATION_FAILED、UNSUPPORTED_HISTORY |
| D | INVALID_REQUEST、NOT_FOUND、UPLOAD_TOO_LARGE、UNSUPPORTED_FILE、INTERNAL_ERROR |

参数问题通常映射 422，对象缺失 404，上传超限 413，类型不支持 415，模型或索引未就绪/超时 503，内部失败 500。坏 PDF 与空文本导入返回 422 并保留管理诊断记录。/ask 遵循完整 AnswerResponse；不要把有 error 属性的任意对象当作失败，业务状态须按明确规则识别。

### 统一数据对象

模块边界使用可 JSON 序列化的 dict/list；内部可自行使用类。D 在 API 层实现验证模型。必须使用以下字段，扩展字段不得替换核心字段。

**Document**

~~~json
{
  "doc_id": "d_012345abcdef",
  "title": "文献标题",
  "authors": ["作者甲"],
  "year": 2023,
  "topics": ["信息检索"],
  "language": "en",
  "source_url": null,
  "rights_note": "组员确认可用于课程项目",
  "file_sha256": "<原始文件完整 SHA256>",
  "status": "ready",
  "error_code": null,
  "error_message": null,
  "page_count": 8
}
~~~

year 允许 null；authors/topics 为数组；language 使用 zh/en/mixed/unknown。缺失作者和年份不让模型猜测。元数据标题必须非空，可暂用文件名并注明待核验。文献 ID 使用文件哈希的稳定映射，并检测截短冲突。状态为 uploaded/parsing/indexing/ready/failed。A 解析成功后返回 indexing，D 在 B 成功构建索引后才设置 ready；解析完成的 indexing 文献可作为候选建索引输入。索引失败保留可重试状态和错误，不虚报 ready。API 默认只展示可服务的 ready 文献，管理页可查看全部状态。

**Chunk**

~~~json
{
  "chunk_id": "c_012345abcdef_p0003_0001",
  "doc_id": "d_012345abcdef",
  "pdf_page": 3,
  "printed_page": null,
  "section": null,
  "text": "来自 PDF 第三页的原文片段。",
  "page_char_start": 0,
  "page_char_end": 19,
  "token_count": 24,
  "document": {
    "title": "文献标题",
    "authors": ["作者甲"],
    "year": 2023,
    "topics": ["信息检索"],
    "language": "en"
  }
}
~~~

上例偏移与 token 数只示意字段，真实值由程序计算。pdf_page 为从 1 开始的 PDF 文件页序号；printed_page 为可空字符串，不混用。偏移是清洗后规范页面文本的半开区间 [start,end)，必须满足 text == normalized_page_text[start:end]。Chunk 中 document 是检索用元数据快照，由 A 联表生成。chunk_id 在相同文件和切块配置下稳定；配置变更由新的 index_version 区分。本版冻结馆藏后不提供页面清洗在线改写。

**Filters**

~~~json
{"year_from": null, "year_to": null, "topics": []}
~~~

年份范围包含边界；year_from 大于 year_to 时返回校验错误。只接受明示的结构化过滤条件。初版不把问题中的“最近几年”自动转成隐藏年份过滤。

**RetrievalHit**

~~~json
{
  "rank": 1,
  "chunk": {"...": "完整 Chunk 对象"},
  "scores": {"bm25": null, "cosine": 0.71, "rrf": 0.03, "rerank": null},
  "matched_by": ["vector"],
  "index_version": "idx_20261003_001"
}
~~~

rank 从 1 开始；未运行的评分填 null；scores 是排序信息，不是答案可信概率。关键词、向量、混合模式分别为 keyword/vector/hybrid。不同分支的原始分数不直接相加。所有返回片段来自同一有效索引快照。

**AskRequest**

~~~json
{
  "question": "有没有不用准确关键词就能找到论文的方法？",
  "filters": {"year_from": null, "year_to": null, "topics": []},
  "history": []
}
~~~

第一版 history 必须为空；非空返回 UNSUPPORTED_HISTORY，不静默装作支持多轮。确认完成单轮后再协商扩展。

**QueryPlan**

~~~json
{
  "original_query": "用户原问题",
  "intent": "explain",
  "rewritten_query": "保留原意的检索表达",
  "keywords": ["语义检索"],
  "needs_clarification": false,
  "clarification_question": null,
  "clarification_options": []
}
~~~

intent 为 find/explain/compare/clarify。查询改写失败时可回退原问题并记录降级原因；不能虚构澄清选项所对应的馆藏。澄清选择与原问题组合为新的独立请求。

**AnswerResponse**

~~~json
{
  "request_id": "q_001",
  "status": "answered",
  "query_plan": {"...": "完整 QueryPlan 对象"},
  "claims": [
    {"claim_id": "cl_1", "text": "一条可核验的回答结论。", "evidence_ids": ["ev_1"]}
  ],
  "evidence": [
    {
      "evidence_id": "ev_1",
      "chunk_id": "c_012345abcdef_p0003_0001",
      "doc_id": "d_012345abcdef",
      "title": "文献标题",
      "authors": ["作者甲"],
      "year": 2023,
      "pdf_page": 3,
      "printed_page": null,
      "quote": "数据库中的原文。",
      "file_url": "/documents/d_012345abcdef/file#page=3"
    }
  ],
  "related_documents": [{"doc_id": "d_012345abcdef", "title": "文献标题"}],
  "limitations": [],
  "clarification_question": null,
  "clarification_options": [],
  "index_version": "idx_20261003_001",
  "timings_ms": {"planning": 0, "retrieval": 0, "generation": 0, "total": 0},
  "error": null
}
~~~

status 为 answered/needs_clarification/insufficient_evidence/error。answered 的 claims 必须非空且每条有可解析证据；其他状态 claims 为空。无检索时 index_version 允许 null。needs_clarification 必须包含追问；insufficient_evidence 包含原因，可附相关文献；error 包含 {"code": "...", "message": "..."}。全部字段保留，未使用项设为空数组、null 或 0。服务器耗时用毫秒。

证据由 C 从本次选中 Chunk 的数据库或索引快照构造，不信任模型生成的标题、页码、链接和引文。第一版 quote 可以直接取完整 Chunk.text；模型只返回 claim 文本和 chunk_id 列表。合法引用不代表语义正确，语义支持需要人工评估。

**IndexManifest**

字段至少包括 index_version、contract_version、built_at、embedding_model、embedding_revision、dimension、normalized、chunking_config、tokenizer、document_count、chunk_count、corpus_hash。corpus_hash 覆盖规范化文本和检索元数据；元数据修改后也需要重建。built_at 用明确带时区的 ISO 8601 时间。manifest 与文本快照、词项索引、向量一起保存。

### HTTP 规格

| 方法与路径 | 请求 | 成功响应 |
|---|---|---|
| GET /health | 无 | 状态、real/mock、模型是否配置、当前索引版本 |
| POST /documents | multipart：file 和 metadata_json 字符串 | {"document": Document, "index_version": "..."} |
| GET /documents | year_from、year_to、topics 可重复参数 | {"documents": [Document]} |
| GET /documents/{doc_id} | 路径 ID | {"document": Document} |
| GET /documents/{doc_id}/file | 路径 ID | application/pdf |
| GET /chunks/{chunk_id} | 路径 ID | {"chunk": Chunk} |
| POST /search | {"query": "...", "filters": Filters, "mode": "hybrid", "top_k": 20} | {"hits": [RetrievalHit], "documents": [...], "index_version": "..."} |
| POST /ask | AskRequest | AnswerResponse |
| POST /feedback | {"request_id": "...", "rating": "useful", "comment": ""} | {"saved": true} |

POST /documents 采用同步导入与全量重建，适合当前小馆藏。D 先取得包括 indexing 状态的完整候选文本块，B 成功生成新索引后再把新文献设为 ready；文献处理失败不得返回成功。已服务索引在失败时继续可用。构建与查询用锁或快照机制，保证单次请求不会混用版本。为了简化这项要求，第一版采用单进程后端和显式读写互斥，不支持多 worker。

/search 中 documents 按 hits 首次出现顺序聚合文献，每项包含 doc_id/title/authors/year/best_rank/preview；hits 保持片段级。top_k 范围 1–50。question/query 去除首尾空白后不得为空，默认最长 2000 字符。支持的上传文件大小上限默认 25 MB，可配置。

非问答接口统一错误体 {"error": {"code": "...", "message": "..."}}；422 为参数非法，404 为对象不存在，413 为超限，415 为不支持类型，503 为服务未就绪。/ask 的正常 answered、needs_clarification、insufficient_evidence 返回 200；status=error 根据原因返回 422/503/500，仍遵守完整 AnswerResponse。日志不得包含密钥。第一版 GET /health 与管理页面须说明上传入口仅适用于本地可信课堂环境。

### 共同验收与测试数据

端到端必测：正常 PDF 导入、重复导入、空文本/坏 PDF、精确搜索、日常表达搜索、年份/主题过滤、引用展开与 PDF 页定位、需要澄清、证据不足、无模型或模型超时、重启加载索引、重建失败保留旧索引。

全组共建约 60 题，每人约 15 题，另一位成员复核。D 汇总为 JSONL，一行一题：

~~~json
{
  "question_id": "t001",
  "split": "test",
  "category": "vague",
  "question": "有没有不用准确关键词就能找到论文的方法？",
  "filters": {"year_from": null, "year_to": null, "topics": []},
  "expected_status": "answered",
  "reference_points": ["指出语义检索并说明作用"],
  "relevant_doc_ids": ["真实馆藏文献 ID"],
  "relevant_chunk_ids": ["真实支持片段 ID"],
  "evidence_groups": [["支持同一要点的可替代片段 ID"]],
  "clarification_expectation": null
}
~~~

category 为 exact/vague/clarify/multi_document/unanswerable。建议数量 10/15/10/15/10；split 为 dev/test。近似改写不得跨集合；只用 dev 调参。片段变化需重新核验标注。多文献题按要点标注 evidence_groups，用于判断证据是否覆盖完整答案。无答案题相关 ID 为空。

报告必须区分：自动结构检查、人工语义核验、真实模型实验与 mock 测试。引用 ID 存在不等于支持结论；相似度不等于正确率。不得为达到指标而修改测试题或伪造证据。
