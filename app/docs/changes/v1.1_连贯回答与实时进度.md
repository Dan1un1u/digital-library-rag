# v1.1 连贯回答与实时进度

日期：2026-10-18。承接 v1.0 的双语检索、正文重排与相邻片段证据策略。

## 问题与处理

系统原先已经接入硅基流动上的 `Qwen/Qwen2.5-32B-Instruct`。问题并非缺少生成模型，而是生成提示偏向独立事实，界面又在每条事实后插入引用按钮，导致阅读零散。此次继续使用现有模型，无需新增 DeepSeek API。

回答提示现在要求先直接回应问题，再综合本次选中的证据写连贯说明。模型在同一次生成中返回 claims 和 sections；sections 只含简短主题与结论序号，不允许另写无引用的事实。服务校验序号完整、不重复且属于本次结论，随后转换为公共 `answer_sections`，用服务生成的 claim_id 组织自然段。旧客户端和没有 sections 的合法输出仍兼容；旧输出按一个段落显示。

页面先显示自然段回答与句末引用编号，再提供“查看原文”按钮和默认折叠的证据。引用中的原文、文献和页号仍来自索引，未让模型生成这些字段。“系统理解”默认折叠。证据不足时仍明确说明，模型自身知识不能冒充馆藏证据。

## 实际阶段进度

新增 `POST /ask/jobs`，返回 HTTP 202 和 job_id；`GET /ask/jobs/{job_id}` 返回阶段、已经经过的阶段、实际用时与完成后的完整 AnswerResponse。原有 `POST /ask` 保留同步行为。

界面每 0.5 秒读取任务状态，在宽屏右侧显示进度；窄屏按 Streamlit 响应布局纵向显示。阶段由后台实际执行位置报告，包含排队、等待读取、规划、检索、证据选择、回答生成、必要时的格式修复、引用结构校验和完成或失败。很短的阶段可能来不及作为当前状态被轮询捕捉，但会出现在已经经过的阶段记录中。没有虚构百分比或模型 token 进度；生成等待期间持续更新已用时。

状态读取使用独立的锁，不会被覆盖整个问答过程的馆藏锁阻塞。单 worker 串行执行任务，默认最多 8 个未完成任务，保留最多约 32 个任务记录，已完成结果保留 15 分钟并在后续提交时清理；服务重启清空任务。队列满返回 503，未知或过期任务返回 404。后台异常只返回安全错误，不暴露服务商响应或密钥。前端等待上限为 5 分钟，超时会提醒后台任务可能还在继续，未实现取消及断线自动恢复。

## 延迟与模型选择

通常仍为 2 次生成服务调用：查询规划一次，最终回答一次；只有格式或引用结构校验失败时才最多修复一次。段落组织与进度显示未增加模型调用。双语混合检索仍会产生中英文各一次查询嵌入请求。

真实请求“大语言模型是如何读取长文本的”本次服务检查用时约 17.2 秒：规划 3.24 秒、检索 0.36 秒、证据选择 0.009 秒、生成 13.63 秒；同问题浏览器验证约 14.9 秒。属于开发单次观察，不能当作稳定延迟或正式效果成绩。当前耗时主要来自生成服务，进度显示改善等待可见性，并未宣称缩短模型本身的响应时间。

本次回答整合了长文本输入能力与相关信息位置影响，并明确说明馆藏没有覆盖完整底层读取机制。换成 DeepSeek 并不能补齐馆藏缺失的证据；后续若切换模型，需要分别验证上下文上限、JSON 输出兼容性、引用正确性及实际延迟。
