# PERF-001 新增文献逐篇触发全馆索引重建

- 登记日期：2026-10-20；来源：COL-006 六篇重新入库检测，用户明确要求登记。
- 状态：已确认，开放、待修复。
- 类型：入库性能缺陷。
- 归属：[COL-006](COL-006.md) 的检测发现，追加至[PR16](https://github.com/Dan1un1u/digital-library-rag/pull/16)；本次仅登记，后续修复独立开展。
- 受测应用版本：main `446f7b5a18b4ebdcc83638618827c802f0416be8`；检测执行提交 `f19f94b178afd4f1c28ab224488ad1a2415fae3b`，应用源码与该 main 一致。

## 触发与实际行为

已有有效索引的馆藏新增一篇文献，经正常 `POST /documents/jobs` 入库。当文献进入 `indexing` 状态时，系统重新读取全馆候选片段，为全部候选片段请求向量计算、重建词法索引并保存新索引。连续新增多篇会逐篇重复这套全量过程，未复用旧索引中未变化片段的向量。

同一文件已为 `ready` 且有效索引存在时，当前代码会跳过重建；该缺陷不是所有重复上传都会触发。

## 白盒原因与影响

1. [Services.ingest](../../app/src/dlrag/api/services.py#L108) 在新增文献未就绪时调用 `self.rebuild()`（第129行）。
2. [Services.rebuild](../../app/src/dlrag/api/services.py#L86) 读取 `store.list_chunks(include_indexing=True)`，把全馆候选片段传给 `retriever.build(candidates)`（第96行）。
3. [Retriever.build](../../app/src/dlrag/retrieval/retriever.py#L208) 将全部候选片段传入 `_encode(...)`（第221行），随后重建全量词法索引与索引文件；没有读取旧向量来复用未变内容。

因此，新增少量文献也会重复处理已有馆藏，增加计算、存储写入及入库等待；使用计费的向量服务时，还会产生重复请求带来的费用。馆藏越大，重复处理的数据量越大，本轮尚未进行多种规模的性能基准。

另据代码分析，`ingest`、`rebuild` 与 `search`、`health` 等方法共用同一把服务锁，同实例的相关请求可能等待导入结束。这是代码层面的影响判断，本轮没有把并发阻塞作为实测结果；检测时正式服务运行在独立实例。

## 期望与后续验收方向

正常新增文献应复用未变化内容的向量，按需更新检索索引；需全量重建的模型、切分或配置变更应有明确触发条件。

后续修复应在独立开发库验证：新增文献时实际编码的片段数和阶段耗时、连续新增时已有片段的复用情况，以及新旧文献检索、索引一致性、失败后保留旧有效索引。性能对比需使用相同馆藏、模型及配置，不能用本轮入库总耗时冒充纯索引基线。

本次没有修改应用、重跑入库或开展性能修复测试；正式馆藏保持现状。后续修复另建分支与PR，本记录PR保持Draft、不合并。
